# Failure Analysis

## Purpose

This document records real failure cases found while testing the Job Market Intelligence and Application Advisor system.

Instead of only reporting successful outputs, I tested the system with different job postings and recorded cases where the extraction, scoring, or legitimacy analysis produced incorrect or unreliable results.

---

## Failure 1: Incorrect or Incomplete Job Extraction

### Posting

Developer — New Market Group (NMG)

### What Happened

The extractor correctly identified most basic information, including the job title, company, location, technical skills, education, responsibilities, and salary range.

However, two important extraction problems were found.

First, the original posting required approximately 10 years of Developer experience, but the structured result only recorded:

`Intermediate Developer`

This removed an important quantitative experience requirement.

Second, the salary range was correctly extracted as:

`110000–130000`

but the system assigned the currency as:

`USD`

The posting itself did not explicitly provide enough evidence to support this currency value.

### Why This Matters

Both fields can strongly affect later analysis.

Missing a required number of years of experience can cause the Application Advisor to overestimate candidate fit.

Inferring an unsupported salary currency can also make market salary analysis inaccurate.

### Likely Cause

The LLM summarized the experience requirement instead of preserving the explicit quantitative requirement.

For the salary currency, the model appears to have inferred information instead of returning null when the source did not explicitly provide a reliable currency.

### Improvement

Extraction prompts and validation should emphasize that high-impact factual fields must remain grounded in the source posting.

If years of experience are explicitly stated, they should be preserved.

If a currency or other factual value is not clearly present, the extractor should return null instead of guessing.

## Failure 2: Fit Score and Recommendation Label Did Not Match

### Posting

Software Developer, Early Career, Campus — Google

### What Happened

The Application Advisor produced a fit score of:

**80/100**

The scoring breakdown was reasonable:

- Educational Alignment: 20/30
- Core Technical Skills: 35/40
- Project & Practical Experience: 20/20
- Workflow & Methodology: 5/10

However, the generated recommendation described the role as:

**"Stretch but may still be worth applying."**

This does not match the intended scoring policy.

The scoring policy defines:

- 80%+ = strong fit
- 50–79% = good fit / encourage applying
- 30–49% = stretch but may still be worth applying
- Below 30% = major growth target

Therefore, an 80/100 score should have been classified as a **strong fit**, not a stretch.

### Why This Matters

The numeric score and recommendation are both user-facing decision-support outputs.

If they contradict each other, a user may not know which result to trust.

For example, a candidate could incorrectly avoid applying to a position even though the system's own numeric score indicates a strong match.

### Likely Cause

The numeric scoring and recommendation wording were generated by the LLM instead of enforcing a deterministic relationship between them.

The model produced reasonable individual factor scores but independently selected an incorrect recommendation category.

### Improvement

The recommendation category should not be independently generated by the LLM.

After the numeric score is calculated, application code should deterministically map the score to the required category.

For example:

- score >= 80 → Strong fit
- score >= 50 → Good fit / encourage applying
- score >= 30 → Stretch but may still be worth applying
- score < 30 → Major growth target

The LLM can still generate the explanation, but the category itself should come from deterministic application logic.

## Failure 3: Legitimacy Analysis Failed on a Synthetic Scam Posting

### Posting

Junior Software Developer — NorthStar Digital Solutions

Synthetic evaluation posting.

### Expected Result

**RED / Highly suspicious**

The synthetic posting deliberately included major recruitment-scam signals:

- Social Insurance Number requested before employment
- Banking information requested upfront
- Passport or driver's licence requested
- $750 equipment payment
- $250 training deposit
- Generic Gmail recruiter address
- Immediate-hiring urgency
- Unverified synthetic company domain

### Initial Result

During the first live run, the legitimacy assessment did not successfully produce its intended structured result.

The system reported an error similar to:

`Unexpected non-whitespace character after JSON`

Because structured parsing failed, the system used its cautious fallback rather than the expected RED assessment.

A second problem also appeared during the same test.

Web research returned similarly named organizations, and the legitimacy investigation selected:

`digitalliteracyassessment.org`

for WHOIS/RDAP lookup even though this was not the domain supplied in the synthetic posting.

This showed that search results from a similarly named organization could contaminate the company identity.

### Why This Matters

This failure occurred in the safety-related part of the advisor.

A suspicious posting should not become less suspicious simply because an LLM returned malformed structured output.

Also, WHOIS information is only useful if the system has identified the correct company domain. Looking up an unrelated domain could produce misleading green signals and make a scam posting appear more trustworthy.

### Likely Causes

There were two causes.

#### 1. Structured Output Formatting

The free LLM sometimes returned a valid JSON object followed by additional text.

The parser attempted to parse the entire response and failed even though a usable JSON object was present.

#### 2. Company Identity Contamination

The research logic allowed search-result domains from similarly named organizations to influence company identity without enough evidence connecting those domains to the actual posting.

### Fix Implemented

The system was updated with targeted changes.

For structured output:

- Added safe recovery of one clear balanced JSON object.
- Markdown fences and trailing non-JSON content can be cleaned when recovery is unambiguous.
- The strict Zod schema is still used.
- Ambiguous responses still use the cautious fallback.
- Recovery activity is visible in verbose logging.

For company identity:

- Explicit domains found in the posting now have priority.
- Generic recruiter domains such as Gmail remain visible as legitimacy signals but are not treated as company WHOIS domains.
- Search-result domains require stronger evidence tying them to the exact company.
- Unverified company identity is treated as uncertainty rather than guessed.
- Sensitive PII, payment, government-ID, generic-email, and urgency signals are extracted directly from the posting.

### Result After Fix

The same synthetic posting was run again.

The system correctly identified the explicit posting domain:

`northstar-digital-careers-example.com`

WHOIS/RDAP could not verify the domain.

The system also directly detected high-priority signals including:

- Sensitive PII requested before employment
- Banking information requested upfront
- Government identification requested upfront
- Generic recruiter email domain

The legitimacy structured response required JSON recovery, but the recovery succeeded safely and passed schema validation.

The final verdict was:

**RED — 100% confidence**

This matched the manual expected result.

### Remaining Limitation

Although the legitimacy verdict was corrected, some downstream Cover Letter Guidance and Interview Prep content still contained references to similarly named companies and industries found during web research.

This means company-identity grounding improved significantly but is not completely solved for all downstream generated sections.

A future improvement would be to prevent all company-specific downstream content from using secondary research unless the company identity has been verified.

## Additional Observation: High Fit Does Not Mean Legitimate

The synthetic NorthStar posting received approximately:

**85/100 — Strong fit**

while its legitimacy verdict was:

**RED — 100% confidence**

This result is reasonable because the synthetic posting was intentionally written with technical requirements that closely matched the resume.

This demonstrates an important design principle of the Application Advisor:

**Job fit and job legitimacy are separate questions.**

A candidate can be highly qualified for the requirements written in a posting while the posting itself is fraudulent.

Therefore, the system should evaluate legitimacy independently and display it before application-fit guidance.

---

## Overall Failure Analysis

Testing revealed failures in three different parts of the system:

| Area | Failure | Impact |
|---|---|---|
| Extraction | Missing experience detail and unsupported salary currency | Could distort market and fit analysis |
| Fit scoring | 80/100 score mapped to a stretch recommendation | Could discourage an appropriate application |
| Legitimacy | Malformed structured output and incorrect company identity | Could weaken scam detection |

The most important lesson from these failures is that LLM output should not be trusted without deterministic validation and grounding.

Structured schemas helped detect malformed outputs, but schemas alone were not enough. The system also needed recovery logic, deterministic score-to-category mapping, direct evidence extraction, and stricter company-identity verification.

The evaluation also showed the value of testing with deliberately different cases. A senior C++ role tested low-fit scoring, an Early Career Google role tested strong-fit scoring, and a synthetic scam posting tested legitimacy and failure recovery.

These failures and fixes made the final system more reliable than the initial implementation while also showing where further improvements are still possible.
